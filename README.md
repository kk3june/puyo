# PUYO ROOM

Next.js + TypeScript + Canvas로 만든 3분 컬러 퍼즐 웹서비스입니다. 게임은 비회원에게 열려 있고 카카오 로그인 사용자만 서버에서 검증된 점수를 랭킹에 등록할 수 있습니다. 자체 제작한 CSS/Canvas 그래픽을 사용합니다.

## 실행

Node.js 22 이상, pnpm 11을 사용합니다.

```sh
pnpm install
pnpm dev
```

http://localhost:3000 에서 실행됩니다. 환경변수가 없어도 게임과 기기별 최고 점수는 작동합니다. 이때는 연습 모드이고 카카오 로그인, 온라인 랭킹, GA4는 비활성화됩니다. 가짜 랭킹 데이터는 표시하지 않습니다.

`.env.example`을 참고해 `.env.local`을 만들고 필요한 값을 설정합니다. 비밀키는 채팅이나 Git에 올리지 마세요.

## 게임

### 일본 공식 참고 자료

2026-09-28 조사. SEGA가 직접 공개한 일본어 자료를 우선 참고합니다. 아래 자료를 찾은 것과 현재 엔진의 공식 규칙 일치 검증은 별개입니다.

- [『ぷよぷよeスポーツ』공식 WEB 매뉴얼](https://manual.sega.jp/puyopuyo_esports/): 기본 조작·기본 규칙·레슨·챌린지의 우선 참고 자료입니다. 기본 규칙은 메뉴의 「基本ルール」, 1인 점수 경쟁은 「チャレンジ」에서 확인합니다.
- [SEGA 공식 대회 규정: 2022 TOCHIGI](https://esports.sega.jp/2022tochigi/regulation.html): 당시 『ぷよぷよeスポーツ』의 通 규칙과 설정을 확인할 수 있습니다. 2인 대전에서는 퀵 드롭 OFF, 제거 개수 4, 방해뿌요 레이트 70 등을 명시합니다. 과거 특정 대회의 설정이며 현재 모든 모드의 공통 사양으로 취급하지 않습니다.
- [『ぷよぷよテトリス2S』공식 WEB 매뉴얼](https://manual.sega.jp/puyopuyotetris2/S/jp/index.html): 소멸·연쇄·상쇄·동시 소멸·전부 제거와 모드별 퀵 드롭 설명을 교차 확인하는 보조 자료입니다. 다른 작품이므로 규칙을 그대로 혼합하지 않습니다.

구현 기준 작품·모드는 아직 확정하지 않았습니다. 현재의 3분 제한, Space 즉시 낙하, 단순화된 회전·종료 판정은 이 서비스의 구현이며 공식 모드와 동일하다고 보장하지 않습니다.

이번 조사에서는 점수 배율표 전체, 낙하 보너스의 정확한 상한, 숨겨진 행, 회전 보정 및 접지 시간의 공식 수치 근거까지 확보하지 못했습니다. 해당 항목은 미검증으로 남기고, 명시적 공식 설명 또는 버전·모드를 기록한 실제 게임 대조로 검증합니다. 기존 코드의 테스트 통과만으로 공식 규칙 일치를 주장하지 않습니다.

### 현재 구현

- 6열 × 12행, 4색, 3분 스프린트. 상하좌우로 4개 이상 연결하면 제거되고 중력 적용 후 다시 연결되면 연쇄입니다.
- 방향키 좌/우: 이동, 위 또는 X: 시계 방향 회전, 아래: 빠르게 내리기, Space: 바로 놓기.
- 터치: 보드를 좌우로 밀면 손가락을 따라 한 칸씩 이동하고, 탭하면 회전합니다. 아래로 천천히 끌면 빠르게 내리고, 아래로 빠르게 튕기면 바로 놓습니다. 조작 버튼은 왼손(← ↓ →)과 오른손(바로 놓기, 회전)으로 나뉘어 있습니다. 누르는 즉시 반응하고, 이동 버튼은 길게 누르면 170ms 뒤부터 60ms 간격으로 반복합니다. 모든 터치 조작은 키보드와 같은 5가지 액션으로 기록되므로 서버 검증 규칙(`sprint-v3`)은 그대로입니다. 키가 작은 화면에서는 보드 크기를 줄여 보드와 버튼이 한 화면에 들어오게 합니다.
- 생성 위치가 막히거나 제한 시간이 끝나면 종료합니다. 탭을 전환해도 시간은 계속 흐릅니다.
- 현재 소멸 점수 구현 = 제거 개수 × 10 × max(1, 연쇄 보너스 + 연결 보너스 + 색수 보너스). 표는 `src/lib/scoring.ts`에 명시했습니다. 각각의 연결 덩어리 보너스를 합산하며, 떨어져 있는 같은 색 덩어리를 하나로 합치지 않습니다. 공식 수치 근거와의 재검증 대상입니다.
- 현재 낙하 보너스 구현: 아래 버튼으로 실제 이동한 1칸당 1점, 한 조각당 최대 11점입니다. 소멸 배율을 곱하지 않고 합산합니다. 자연 낙하, 막혀서 이동하지 못한 입력, 연출 대기 중 입력, Space 즉시 낙하에는 부여하지 않습니다. 이 수치와 적용 범위도 공식 근거와의 재검증 대상입니다.
- 대전 규칙 기반에는 기본 방해뿌요 레이트 70, 96초 마진타임, 공격 잔여 비율 이월, 자기 큐 우선 상쇄, 최대 30개 낙하를 반영했습니다. 2:2에서는 공격량을 나누지 않고 생존한 상대 두 명에게 각각 전송하며, 상대 팀 전원이 탈락하면 라운드가 종료됩니다. 이 규칙은 1:1 온라인 대전(`/versus`)에 연결되어 있습니다. 2:2는 규칙 계층만 있고 화면은 없습니다.
- 게임 종료 후 로그인해도 현재 탭에 완료 기록이 남습니다. 로그인 후 ‘랭킹에 기록 남기기’를 누르세요. 게임 시작으로부터 24시간 내에 등록할 수 있습니다. 새 게임을 시작하면 미등록 기록을 대체합니다.
- 낙하는 화면 주사율에 맞춰 보간하고, 바로 놓기는 잔상과 착지 반동을 표시합니다. 소멸은 팽창 → 파편 → 중력 낙하 → 다음 연쇄 순서로 진행합니다. OS의 동작 줄이기 설정에서는 흔들림·잔상·파편을 줄이되 게임 시간과 판정은 동일합니다.
- 애니메이션 구간에는 다음 조각의 조작·낙하가 잠시 대기하며 3분 타이머는 계속 진행됩니다. 브라우저와 서버가 동일한 `sprint-v3` 규칙(연출 시간 + 낙하 보너스)으로 검증합니다. 이전 `sprint-v1`/`sprint-v2` 게임도 원래 규칙으로 등록할 수 있고 기존 기록은 보존됩니다. 현재 랭킹과 기기 최고 점수는 새 규칙끼리 비교하며, 예전 기기 기록도 삭제하지 않습니다.
- 랭킹은 사용자별 최고 점수만 표시합니다. 동점이면 먼저 등록한 기록이 앞섭니다. 주간 범위는 한국 시간 월요일 00:00부터입니다.

## 1:1 온라인 대전 (`/versus`)

비용 없이 운영하기 위해 대전은 브라우저끼리 직접 연결하는 P2P 방식입니다. 서버는 두 플레이어를 짝짓고 WebRTC 연결 정보(offer, answer 각 1개)만 중계합니다. 이후 게임 데이터는 서버를 거치지 않습니다.

- **판정**: 먼저 대기한 플레이어가 호스트가 됩니다. 호스트 브라우저가 두 보드를 하나의 결정론적 시뮬레이션(`src/lib/versus.ts`, 규칙 `battle-v1`)으로 진행하며 공격, 상쇄, 방해뿌요 낙하를 판정합니다. 두 플레이어는 같은 뿌요 순서를 받습니다. 시간 제한은 없고 먼저 쌓여 막히는 쪽이 집니다. 같은 틱에 둘 다 막히면 무승부입니다.
- **동기화** (`src/lib/netplay.ts`): 게스트는 입력만 보내고 자기 조작은 즉시 화면에 반영합니다. 호스트가 보내는 확정 입력 스트림으로 보정하며, 승패는 호스트 확정 결과로만 표시합니다. 호스트 응답이 2초 이상 늦으면 게스트 화면이 멈추고, 10초 동안 아무 메시지가 없으면 대전을 종료합니다.
- **한계**: 친선전 전용이라 기록이나 레이팅을 저장하지 않습니다. 판정이 호스트 기기에서 이뤄지므로 조작된 클라이언트를 막을 수 없습니다. 게스트에게는 네트워크 지연만큼 불리합니다. 연결은 공개 STUN만 쓰고 TURN 중계가 없어서, 일부 엄격한 네트워크(일부 모바일 통신망 등)에서는 연결이 실패할 수 있습니다.
- **매칭 저장소**: `supabase/migrations/202611020001_versus_matchmaking.sql`을 적용하면 Supabase를 씁니다. 이때 필요한 것은 `NEXT_PUBLIC_SUPABASE_URL`과 `SUPABASE_SERVICE_ROLE_KEY`뿐이고, 카카오 설정은 필요 없습니다. Supabase가 없으면 로컬 개발용 메모리 저장소를 쓰는데, 프로세스 하나에서만 동작하므로 Vercel에서는 503을 반환합니다. 플레이어는 익명 `puyo_guest` 쿠키로 구분합니다.

## Supabase와 카카오 로그인

1. Supabase 프로젝트를 생성하고 `supabase/migrations/`의 SQL 파일을 파일명 순서로 실행합니다. 기존 설치에는 아직 적용하지 않은 마이그레이션만 추가 적용합니다.
2. 프로젝트 URL을 `NEXT_PUBLIC_SUPABASE_URL`에 입력하고 서버 전용 service role key를 `SUPABASE_SERVICE_ROLE_KEY`에 넣습니다. service role key는 브라우저에 노출하지 않습니다.
3. `openssl rand -hex 32`로 생성한 문자열을 `GAME_SIGNING_SECRET`에 설정합니다.
4. Kakao Developers에서 앱을 만들고 카카오 로그인을 활성화한 뒤 REST API 키를 `KAKAO_REST_API_KEY`, 활성화한 Client Secret을 `KAKAO_CLIENT_SECRET`에 입력합니다.
5. **카카오 Redirect URI**에 `http://localhost:3000/auth/callback`과 `https://<서비스도메인>/auth/callback`을 등록합니다. 이메일·닉네임·프로필 권한은 요청하지 않습니다.
6. `NEXT_PUBLIC_SITE_URL`은 접속할 정확한 origin으로 설정합니다. 로컬 기본값은 `http://localhost:3000`입니다. 포트를 변경하면 함께 바꾸세요.

앱 서버가 카카오 OAuth 코드 교환과 사용자 조회를 직접 수행합니다. 첫 로그인 때 Supabase Auth에 내부 계정을 만들고 `kakao_accounts` 테이블에 카카오 식별자와 연결합니다. 공개 이름은 카카오 프로필 대신 `젤리-<내부 식별자 일부>`이며, 카카오 이메일·닉네임·프로필은 요청하거나 저장하지 않습니다. 로그인은 `GAME_SIGNING_SECRET`으로 서명한 HttpOnly 쿠키로 유지합니다.

공식 설정 문서: [Kakao Login REST API](https://developers.kakao.com/docs/latest/ko/kakaologin/rest-api), [Supabase Admin API](https://supabase.com/docs/reference/javascript/auth-admin-createuser).

## Google Analytics 4

1. GA4 속성의 웹 데이터 스트림을 만들고 `G-...` 측정 ID를 `NEXT_PUBLIC_GA_MEASUREMENT_ID`에 넣습니다.
2. 배포 환경에서 변경했다면 다시 빌드/배포합니다. 공개 환경변수는 빌드 시 번들에 포함됩니다.
3. **웹 스트림의 Enhanced Measurement(향상된 측정)는 끕니다.** 앱이 직접 `page_view`와 필요한 이벤트만 보내므로 자동 URL/history 측정 및 중복 이벤트를 피합니다. `page_view`에는 쿼리스트링 없는 URL만 전달합니다.
4. 사용자 동의 후에만 스크립트를 로드합니다. 거절하면 GA 네트워크 요청을 만들지 않습니다. 광고 관련 동의와 Google Signals는 비활성화했습니다.
5. 이벤트: `page_view`, `game_start`, `game_end`, `login_click`, `login`, `score_submit`, `leaderboard_view`. 점수, 연쇄, 게임 시간, 모드 등만 보내며 계정 ID/이메일/별명을 보내지 않습니다.
6. 동의한 실제 브라우저에서 게임 종료 및 기록 저장 후 GA Realtime에서 확인합니다. DebugView는 Tag Assistant 등으로 디버그 모드를 켜고 확인할 수 있습니다.

현재 페이지는 일반 문서 이동 방식으로 렌더링됩니다. 추후 클라이언트 라우팅을 추가하면 route 변경에 대한 page_view를 추가해야 합니다.

공식 문서: [GA4 수동 페이지뷰](https://developers.google.com/analytics/devguides/collection/ga4/views).

## Vercel 배포

1. 이 디렉터리를 새 Git 저장소에 올리고 Vercel에서 Next.js 프로젝트로 가져옵니다. 빌드 명령은 `pnpm build`입니다.
2. `.env.example`의 값을 Vercel 환경변수에 등록합니다. service role과 게임 서명키에는 절대로 `NEXT_PUBLIC_` 접두사를 붙이지 않습니다.
3. 최종 도메인에 맞게 `NEXT_PUBLIC_SITE_URL`, Supabase Site URL과 Redirect URL을 설정하고 배포합니다. Preview 배포를 별도로 테스트하려면 해당 origin/redirect를 정확히 등록하세요.
4. Supabase 마이그레이션을 적용한 뒤 비회원 플레이 → 카카오 로그인 → 기존 게임 등록 → 다른 브라우저에서 랭킹 확인 → GA4 이벤트 수신을 실제 계정으로 점검합니다.
5. 공개 전 개인정보 안내 페이지의 운영자·연락처·보유 기간 등 운영 정보를 확정하여 반영합니다. 서비스명도 최종 확정하세요.

실제 배포, 카카오 OAuth 인증 완료, 원격 DB 저장, GA 수신은 해당 서비스 프로젝트와 키를 연결한 후에 확인할 수 있습니다.

## 점수 검증과 범위

서버는 서명된 시드/세션을 발급하고 HttpOnly 브라우저 쿠키에 연결합니다. 등록 시 카카오 계정을 검증하고, 50ms 단위 조작 로그를 동일한 규칙 엔진으로 재생해서 점수를 계산합니다. 클라이언트의 점수 필드는 믿지 않습니다. 입력 횟수/순서, 종료 상태, 경과 시간, 만료, 서명을 확인하고 세션 기본키로 중복 등록을 차단합니다. DB에는 RLS를 켜고 브라우저 역할의 접근 권한을 제거합니다.

이 방식은 임의 점수 변경을 방지하지만 자동 플레이 봇이나 합법 입력 로그를 생성하는 프로그램까지 판별하지는 않습니다. 큰 규모의 공개 경쟁 서비스에는 별도 요청 제한, 봇 대응, 실시간 서버 권위 방식이 추가로 필요합니다. 랭킹은 단일 플레이 기록만 다룹니다. 1:1 대전은 검증 없는 P2P 친선전이며, 원작의 모든 회전/점수 규칙을 구현한 것은 아닙니다.
